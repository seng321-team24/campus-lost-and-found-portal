## NFR-M2-01 - Performance of listing operations

- **Requirement:** The system shall create a listing (`POST /items`) with a 95th-percentile response time below **3 seconds**, and return the user's own listings (`GET /users/me/items`) with a 95th-percentile response time below **2 seconds**, under a load of **20 concurrent users**.
- **Rationale:** The vision states that a listing can be created "in a few steps"; slow saves break this. 20 concurrent users is a realistic peak for a single campus.
- **Related FR:** FR-M2-01, FR-M2-02, FR-M2-07
- **Measurement method:** Load test with k6 against a test environment seeded with 1,000 listings. The photo upload is excluded (measured separately because it depends on file size).
- **Test procedure:**
  1. Seed the test database with 1,000 listings and 20 test users.
  2. Run the k6 script for 5 minutes with 20 virtual users, each creating a listing and then loading **My Listings**.
  3. Read `http_req_duration` p(95) for each endpoint from the k6 summary.
- **Pass criterion:** p95 < 3000 ms for `POST /items` and p95 < 2000 ms for `GET /users/me/items`; error rate < 1 %.

## NFR-M2-02 - Usability of listing creation

- **Requirement:** A first-time user shall be able to create a complete lost or found listing (including category and location) in **under 2 minutes**, without help.
- **Rationale:** Vision success criterion: "A lost or found listing can be created in under 2 minutes."
- **Related FR:** FR-M2-01, FR-M2-02
- **Measurement method:** Moderated usability test with 3-5 students who have not used the system, using the clickable Figma prototype (Sprint 2) and later the implemented system.
- **Test procedure:**
  1. Give each participant two tasks in alternating order: (a) Lost: "You lost your black leather wallet on the 2nd floor of the library yesterday. Report it." (b) Found: "You found a blue water bottle in the A Block cafeteria and left it at the security office. Report it."
  2. For each task, start the timer when the participant is on **My Listings**; stop it when the success message appears.
  3. Record time, number of errors and whether help was needed, separately for the lost and the found task.
- **Pass criterion:** For **each** task type, at least 80 % of participants finish in under 2 minutes without help (e.g. 4 of 5).

## NFR-M2-03 - Secure photo upload

- **Requirement:** The photo upload endpoint shall accept only **JPEG and PNG** files of at most **5 MB**. Files of another type shall be rejected with `415 Unsupported Media Type`, and larger files with `413 Payload Too Large`. A rejected upload shall not change the listing. The file type shall be checked by file content (magic bytes), not only by extension.
- **Rationale:** Prevents uploading executable or oversized files and protects storage. The 413/415 responses are already defined in `api/openapi.yaml`; the 5 MB limit is pending team approval (the contract says the limit is "to be agreed by the team").
- **Related FR:** FR-M2-06
- **Measurement method:** Automated API tests against `POST /items/{itemId}/photo`.
- **Test procedure:**

| # | Input | Expected result |
| --- | --- | --- |
| 1 | `photo.jpg`, 1.8 MB | `200`, listing has `photoUrl` |
| 2 | `photo.png`, 4.9 MB | `200` |
| 3 | `photo.jpg`, 5.1 MB | `413`, listing unchanged |
| 4 | `document.pdf` | `415`, listing unchanged |
| 5 | `script.exe` renamed to `photo.jpg` | `415` (content check) |

- **Pass criterion:** All 5 cases return the expected status code, and in cases 3-5 the listing's `photoUrl` is unchanged.

## NFR-M2-04 - Owner-only modification

- **Requirement:** Edit (`PUT /items/{itemId}`), close, and photo upload requests for a listing shall succeed only for the listing owner; delete (`DELETE /items/{itemId}`) shall succeed only for the owner or a moderator. All other authenticated users shall receive `403 Forbidden`, and unauthenticated requests `401 Unauthorized`.
- **Rationale:** Prevents users from changing or removing other people's listings (FR-M2-03 authorization rule).
- **Related FR:** FR-M2-03, FR-M2-04, FR-M2-05, FR-M2-06
- **Measurement method:** Automated API tests with three accounts: owner, other user, moderator.
- **Test procedure:** For each of the four operations, send the request as (a) the owner, (b) another user, (c) without a token, and for delete also (d) as a moderator.
- **Pass criterion:** 100 % of edit/close/upload requests by non-owners and 100 % of delete requests by users who are neither owner nor moderator return `403`; delete by a moderator returns `204`; all requests without a token return `401`; and the listing is unchanged after every rejected request.
