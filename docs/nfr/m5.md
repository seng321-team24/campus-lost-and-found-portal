## 2. Requirement Specifications
 
### `NFR-M5-01`: Role-Based Access to Decision Endpoints
* **Category:** Security
* **Description:** Only users with the `STAFF` or `MODERATOR` role may approve or reject claims. Administrator functions (user management, category management, audit log) are limited to `MODERATOR`.
* **Target Metric:** 100% of unauthorized calls return `403 Forbidden` (or `401 Unauthorized` without a valid token). 0 database changes result from unauthorized calls.
* **Test Procedure:**
  1. Create test accounts with roles `STUDENT`, `STAFF` and `MODERATOR`.
  2. Send `POST /claims/{claimId}/decision` with each account and once without a token.
  3. Check the status codes: student `403`, no token `401`, staff and moderator `200`.
  4. Check in the database that the claim status did not change after the `403` and `401` calls.
  5. Repeat for the administrator endpoints with a `STAFF` account (expected `403`).
* **Pass Criterion:** All steps give the expected result.
### `NFR-M5-02`: Traceable Audit Records
* **Category:** Traceability
* **Description:** Every state change that matters for a dispute must be recorded with actor, time, action, target and before/after values. Audit records cannot be changed or deleted through the API.
* **Target Metric:** 20 operations (decisions, handovers, removals, role changes) produce 20 audit records; no record is missing or duplicated; no API endpoint can edit or delete an audit record.
* **Test Procedure:**
  1. Start with an empty audit table in the test database.
  2. Run a script that performs 20 operations of mixed type.
  3. Count the audit records and compare with 20.
  4. Check that each record contains actor, time, action and target.
  5. Try `PUT` and `DELETE` on the audit log path and check that they are not allowed (`404` or `405`).
* **Pass Criterion:** Count equals 20, all fields filled, no modification possible.
### `NFR-M5-03`: Central Role and Permission Rules
* **Category:** Maintainability
* **Description:** The roles and what each role may do are defined in a single permission table/component. Endpoints ask this component and do not compare roles themselves.
* **Target Metric:** 0 role comparisons outside the permission component; the permission table is documented in the architecture document of M5.
* **Test Procedure:**
  1. Search the code base for direct role comparisons (for example `role == "MODERATOR"`).
  2. Check that every endpoint with access rules calls the permission component.
  3. Change one rule in the permission component and check that the matching tests fail or change as expected.
* **Pass Criterion:** No role comparison is found outside the permission component.
